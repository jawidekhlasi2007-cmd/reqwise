- Противоречия в пороговых значениях предупреждений о лимитах.
- Передача финансовых данных в незащищенных push-уведомлениях.

## 5. Проблемы качества

### F-05: Противоречие в пороге срабатывания предупреждения о лимите

- **Критичность:** Высокая
- **Тип:** Противоречие
- **Затрагивает:** REQ-004
- **Нарушенное правило:** ISO/IEC/IEEE 29148:2018 §5.2.6 Consistent (set)
- **Уверенность ИИ:** 100%

В функциональных требованиях указано, что предупреждение отправляется при расходовании 90% лимита, в то время как в интерфейсных требованиях указан порог 80%.

> Предупреждение отправляется при расходовании 90% лимита.

**Почему это проблема:** Разные значения порога для одного и того же бизнес-процесса в разных разделах спецификации приводят к неопределенности при реализации.

**Как исправить:** Привести порог предупреждения к единому значению во всех разделах (например, 90%).

### F-06: Неопределенная метрика нагрузки

- **Критичность:** Высокая
- **Тип:** Производительность
- **Затрагивает:** Весь документ
- **Нарушенное правило:** ISO/IEC/IEEE 29148:2018 §5.2.5 Verifiable
- **Уверенность ИИ:** 95%

Требование к нагрузке сформулировано обще и не содержит числовых показателей (например, RPS, количество активных пользователей).

> Система должна выдерживать высокую нагрузку.

**Почему это проблема:** Без конкретных метрик невозможно провести нагрузочное тестирование и подтвердить выполнение требования.

**Как исправить:** Указать конкретные количественные параметры нагрузки (например, поддержка 5000 запросов в секунду).

### F-07: Антипаттерн проектирования REST API при ошибках

- **Критичность:** Высокая
- **Тип:** Неверное утверждение
- **Затрагивает:** Весь документ
- **Нарушенное правило:** ISO/IEC/IEEE 29148:2018 §5.2.5 Correct
- **Уверенность ИИ:** 95%

Эндпоинт возвращает HTTP статус 200 OK при возникновении ошибок с передачей информации в теле ответа, что нарушает стандарты проектирования REST API.

> При ошибке эндпоинт также возвращает 200 с полем error.

**Почему это проблема:** Возврат статуса 200 OK при ошибках ломает стандартную обработку ошибок сетевыми клиентами, шлюзами и системами мониторинга.

**Как исправить:** Использовать стандартные HTTP коды ошибок (например, 400 Bad Request, 422 Unprocessable Entity) при возникновении ошибок.

### F-08: Логирование конфиденциальных данных в открытом виде

- **Критичность:** Высокая
- **Тип:** Противоречие
- **Затрагивает:** Весь документ
- **Нарушенное правило:** ISO/IEC/IEEE 29148:2018 §5.2.5 Feasible
- **Уверенность ИИ:** 95%

Требование логирования полного номера карты противоречит стандартам информационной безопасности платежных систем (PCI DSS).

> включая тело запроса и номер карты, чтобы упростить разбор инцидентов.

**Почему это проблема:** Сохранение полных номеров карт в логах создает критическую уязвимость и является нарушением нормативов обработки платежных данных.

**Как исправить:** Маскировать или исключать чувствительные данные (номер карты, CVV) из логов.

### F-13: Использование субъективного термина в требовании к скорости

- **Критичность:** Средняя
- **Тип:** Неясная формулировка
- **Затрагивает:** REQ-003
- **Нарушенное правило:** ISO/IEC/IEEE 29148:2018 §5.2.5 Unambiguous
- **Уверенность ИИ:** 95%

Использование слова «быстро» в требовании к отправке уведомления является субъективным и не имеет проверяемого критерия в рамках данного пункта.

> Система должна быстро отправлять push-уведомление

**Почему это проблема:** Слово «быстро» не имеет четкого измеримого эквивалента без отсылки к нефункциональным требованиям.

**Как исправить:** Убрать слово «быстро» или дополнить требование ссылкой на нефункциональное требование по времени отклика (НФТ-2).

### F-14: Использование субъективных качественных характеристик для UI

- **Тип:** Неясная формулировка

> Экран настройки лимита должен быть удобным и интуитивно понятным.

**Почему это проблема:** Отсутствуют метрики юзабилити, что делает критерий приемки невозможным для формальной проверки.

**Как исправить:** Заменить на конкретные требования к интерфейсу или удалить субъективную формулировку.

### F-15: Неизмеримое требование безопасности

- **Тип:** Нельзя проверить
- **Затрагивает:** Весь документ

> Данные клиента должны быть защищены.

**Почему это проблема:** Абстрактные требования безопасности не могут быть проверены однозначным тестом без спецификации конкретных алгоритмов и стандартов.

**Как исправить:** Уточнить требования к защите данных (например, шифрование трафика по протоколу TLS 1.3 и персональных данных в БД по стандарту AES-256).

**Почему это проблема:** Дублирование требований нарушает принципы структурирования спецификации и создает риск рассинхронизации при внесении изменений.

**Как исправить:** Удалить одно из дублирующихся требований (например, REQ-013).

## 6. Проблемы API

### F-09: Использование кода 200 для ошибок в POST /api/v1/limits

- **Критичность:** Высокая
- **Тип:** Контракт API
- **Затрагивает:** REQ-018 (`POST /api/v1/limits`)
- **Нарушенное правило:** RFC 9110 §15 Status Codes
- **Уверенность ИИ:** 95%

Эндпоинт возвращает статус 200 ОК даже в случае возникновения ошибок, передавая информацию об ошибке в теле ответа.

> При ошибке эндпоинт также возвращает 200 с полем error.

**Почему это проблема:** Клиентские приложения и сетевые шлюзы не смогут корректно обрабатывать сбои без стандартизированных кодов ошибок HTTP 4xx/5xx.

**Как исправить:** Использовать стандартные коды ошибок HTTP (например, 400, 422, 500) вместо 200 OK при возникновении ошибок.

**Как исправить:** Описать полную JSON-схему ответа с указанием типов данных, единиц измерения и валюты (KZT).

Логируются полные тела запросов и номера банковских карт, что нарушает требования безопасности и стандарты защиты данных.

> Все запросы к API логируются полностью, включая тело запроса и номер карты

**Почему это проблема:** Сохранение номеров карт и персональных данных в логах создает критическую уязвимость утечки данных.

### F-02: Отсутствие проверки авторизации в POST /api/v1/limits

- **Тип:** Пробел в безопасности

Идентификатор клиента передается в теле запроса без проверки соответствия аутентифицированному пользователю, что позволяет изменять лимиты чужих аккаунтов.

**Почему это проблема:** Злоумышленник может подставить чужой customerId в тело запроса и изменить чужой лимит расходов.

**Как исправить:** Определять идентификатор клиента на основе токена аутентификации, а не принимать его из тела запроса.

### F-03: Логирование конфиденциальных данных и номеров карт

- **Критичность:** Критическая
- **Тип:** Пробел в безопасности

> Все запросы к API логируются полностью, включая тело запроса и номер карты

**Почему это проблема:** Логирование номеров карт (PAN) и персональных данных в открытом виде создает критическую уязвимость утечки данных при несанкционированном доступе к логам.

**Как исправить:** Исключить логирование номеров карт, пин-кодов, токенов и тел запросов, содержащих чувствительные данные. Применять маскирование (например, первые 6 и последние 4 цифры карты).

### F-04: Отсутствие контроля авторизации в API (Broken Object Level Authorization)

- **Критичность:** Критическая
- **Тип:** Пробел в безопасности

Эндпоинты API-1 и API-2 принимают или возвращают данные по идентификатору customerId в теле запроса или пути, но не содержат требований проверки того, что текущий аутентифицированный пользователь имеет право управлять данным customerId.

> POST /api/v1/limits устанавливает лимит. Тело запроса: { "customerId": "..."

**Почему это проблема:** Злоумышленник может подставить чужой customerId и просматривать или изменять чужие финансовые лимиты.

**Как исправить:** Определить, что идентификатор клиента извлекается на сервере из защищенного токена сессии/аутентификации, а не принимается доверенным образом от клиента.

### F-10: Воздействие внутреннего эндпоинта отправки уведомлений

**Почему это проблема:** Внутренний эндпоинт может быть вызван злоумышленниками для спама или подделки уведомлений клиентам.

**Как исправить:** Ограничить доступ к эндпоинту с помощью взаимной аутентификации TLS (mTLS) или внутренних сетевых политик.

### F-11: Передача финансовых данных в push-уведомлениях

- **Критичность:** Высокая
- **Тип:** Персональные данные

- **Уверенность ИИ:** 90%

Требование ФТ-5 требует включать в push-уведомление сумму покупки, остаток лимита и текущий баланс счёта. Push-уведомления отображаются на экране блокировки устройства и могут быть перехвачены или увидены посторонними лицами.

> Уведомление должно содержать сумму покупки, остаток лимита и текущий баланс счёта

**Почему это проблема:** Раскрытие финансовой информации (баланса и остатка лимита) на заблокированном экране смартфона нарушает конфиденциальность данных клиента.

**Как исправить:** Минимизировать данные в уведомлениях: отправлять только факт достижения лимита без указания точного баланса и сумм, либо предоставлять возможность скрывать текст уведомлений.

### F-12: Дублирование требований и несогласованность порогов предупреждений

- **Критичность:** Высокая
- **Тип:** Нормативные требования

> Предупреждение отправляется при расходовании 90% лимита. ... Предупреждение показывается при 80% лимита

**Почему это проблема:** Разные пороговые значения в функциональных требованиях и интерфейсе приводят к дезориентации пользователей и ошибкам реализации.

**Как исправить:** Привести пороговые значения срабатывания предупреждений к единому значению во всех разделах спецификации.

### F-17: Некорректная обработка ошибок HTTP в API

**Как исправить:** Использовать стандартные коды состояния HTTP (400, 401, 403, 404, 500) для различных типов ошибок.

### F-18: Неизмеримые и нечеткие нефункциональные требования

## 8. Недостающие требования

### M-1: Обработка некорректных значений лимита

- **Критичность:** Высокая

В спецификации не описано поведение системы и возвращаемые ошибки при попытке клиента установить лимит вне разрешенного диапазона (менее 1 000 или более 10 000 000 KZT).

**Предлагаемое требование:** Система должна отклонять запрос на установку лимита и возвращать ошибку валидации, если запрашиваемая сумма меньше 1 000 KZT или больше 10 000 000 KZT.

*Нарушенное правило: ISO/IEC/IEEE 29148:2018 §5.2.5 Complete*

### M-2: Поведение транзакций при превышении лимита

- **Критичность:** Высокая

Не определено, блокируется ли расходная операция при достижении/превышении месячного лимита или транзакция проходит успешно с отправкой уведомления.

**Предлагаемое требование:** Система должна разрешать проведение транзакции, даже если она превышает установленный месячный лимит расходов, генерируя при этом соответствующее уведомление.

*Нарушенное правило: ISO/IEC/IEEE 29148:2018 §5.2.5 Complete*

### M-3: Аутентификация API

- **Критичность:** Высокая

В спецификации API не указано, каким образом клиент или процессинговый центр подтверждают свою личность при вызове эндпоинтов.

**Предлагаемое требование:** Все запросы к API должны быть защищены с использованием токенов аутентификации (например, OAuth 2.0 / JWT), проверяемых на стороне шлюза.

*Нарушенное правило: OWASP API2:2023 Broken Authentication*

### M-4: Маскирование данных в логировании

- **Критичность:** Высокая

Необходимо регламентировать требования по безопасному логированию без раскрытия персональных и платежных данных.

**Предлагаемое требование:** Система должна исключать из логов все персональные данные клиентов, секретные токены и полные номера платежных карт (PAN), выполняя их маскирование.

*Нарушенное правило: ISO/IEC/IEEE 29148:2018 §5.2.5 Necessary*

### M-5: Ограничение частоты запросов (Rate Limiting)

- **Критичность:** Средняя

Отсутствуют защитные механизмы против автоматизированного перебора или DoS-атак на эндпоинты изменения лимитов и отправки уведомлений.

**Предлагаемое требование:** Система должна ограничивать количество запросов к API от одного пользователя или IP-адреса (не более 10 запросов в минуту), возвращая статус 429 при превышении.

*Нарушенное правило: OWASP API4:2023 Unrestricted Resource Consumption*

## 10. Предлагаемые исправления

### REQ-001

**Было:** Клиент должен иметь возможность установить месячный лимит расходов в мобильном приложении. Acceptance criteria: лимит сохраняется..

**Предлагается:** Система должна предоставлять авторизованному клиенту возможность установить месячный лимит расходов в диапазоне от [ASSUMPTION: 1000] до [ASSUMPTION: 1000000] рублей в мобильном приложении.

**Что изменено:** Исправлены дублирование, неопределенность и отсутствие измеримых границ значения лимита.

**Как проверить:**

- Дано клиент находится на экране настройки лимита, Когда он вводит валидную сумму 50000 рублей и нажимает кнопку сохранения, Тогда лимит сохраняется в базе данных и отображается на экране.
- Дано клиент вводит сумму вне допустимого диапазона, Когда он пытается сохранить лимит, Тогда система выводит сообщение об ошибке валидации.

### REQ-003

**Было:** Система должна быстро отправлять push-уведомление, когда клиент достигает лимита. Acceptance criteria: none.

**Предлагается:** Система должна отправлять push-уведомление клиенту в течение [ASSUMPTION: 5] секунд с момента достижения расходами 90% установленного месячного лимита.

**Что изменено:** Устранен субъективный термин «быстро» и добавлен проверяемый критерий времени и порога.

**Как проверить:**

- Дано расходы клиента достигли 90% от лимита, Когда транзакция обработана, Тогда система отправляет push-уведомление в течение установленного времени.
- Дано расходы клиента составляют менее 90% от лимита, Когда проверяется состояние, Тогда push-уведомление не отправляется.

### REQ-004

**Было:** Предупреждение отправляется при расходовании 90% лимита. Acceptance criteria: none.

**Предлагается:** Система должна отправлять предупредительное уведомление клиенту ровно в момент, когда сумма его расходов достигает 90% от установленного месячного лимита.

**Что изменено:** Устранено противоречие с UI-требованиями и добавлено условие отправки.

**Как проверить:**

- Дано текущие расходы составляют ровно 90% лимита, Когда поступает новая транзакция, Тогда система генерирует предупреждение.
- Дано расходы составляют 89% лимита, Когда транзакция не увеличивает их до 90%, Тогда предупреждение не отправляется.

### REQ-011

**Было:** Экран настройки лимита должен быть удобным и интуитивно понятным. Acceptance criteria: none.

**Предлагается:** Система должна отображать экран настройки лимита, содержащий поле ввода суммы, кнопку сохранения и текущий баланс, причем время отклика интерфейса при открытии экрана не должно превышать [ASSUMPTION: 1] секунды.

**Что изменено:** Устранены субъективные характеристики «удобным и интуитивно понятным» и добавлены измеримые требования к UI.

**Как проверить:**

- Дано клиент нажал на пункт меню лимитов, Когда открывается экран настройки, Тогда все обязательные элементы управления отображаются.
- Дано клиент открывает экран настройки, Когда замеряется время отрисовки, Тогда оно составляет менее 1 секунды.

### REQ-013

**Было:** Клиент должен иметь возможность задать месячный лимит расходов в мобильном приложении. Acceptance criteria: none.

**Предлагается:** Система должна предоставлять клиенту возможность задать месячный лимит расходов в мобильном приложении с шагом изменения в [ASSUMPTION: 100] рублей.

**Что изменено:** Устранено дублирование с REQ-001 и добавлено конкретное условие шага ввода.

**Как проверить:**

- Дано клиент открыл форму задания лимита, Когда он вводит сумму кратную шагу изменения, Тогда значение принимается системой.
- Дано клиент вводит невалидное значение, Когда пытается сохранить, Тогда система блокирует сохранение.

### REQ-018

**Было:** POST /api/v1/limits устанавливает лимит. Тело запроса: { "customerId": "...", "amount": 50000 }. Возвращает 200 { "status": "ok" }. При ошибке эндпоинт также возвращает 200 с полем error. Acceptance criteria: none.

**Предлагается:** Система должна предоставлять защищенный эндпоинт POST /api/v1/limits с проверкой токена авторизации, который принимает JSON с параметрами лимита, возвращает HTTP-статус 200 OK при успехе или стандартные коды ошибок HTTP (400, 401, 403) при сбоях.

**Что изменено:** Устранены уязвимость авторизации (BOLA), антипаттерн возврата кода 200 при ошибках и отсутствие стандартов API.

**Как проверить:**

- Дано валидный JWT-токен и корректный запрос, Когда отправляется POST /api/v1/limits, Тогда система возвращает статус 200 и JSON с результатом.
- Дано токен отсутствует или указывает на другого пользователя, Когда отправляется запрос, Тогда система возвращает HTTP статус 401 или 403.

### REQ-019

**Было:** GET /api/v1/limits/{customerId} возвращает лимит, сумму расходов и баланс счёта. Acceptance criteria: none.

**Предлагается:** Система должна предоставлять защищенный эндпоинт GET /api/v1/limits/{customerId}, возвращающий в формате JSON установленный лимит, сумму расходов и баланс счета с точностью до копеек и статусом 200 OK.

**Что изменено:** Добавлены требования к формату данных, валюте, точности и защите эндпоинта.

**Как проверить:**

- Дано авторизованный пользователь запрашивает данные своего customerId, Когда отправляется GET-запрос, Тогда система возвращает JSON с полями лимита, расходов и баланса.
- Дано запрашивается несуществующий customerId, Когда отправляется запрос, Тогда возвращается HTTP статус 404.

### REQ-020
